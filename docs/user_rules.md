# User Rules — รูปแบบการทำงานที่เจ้าของโปรเจกต์ชอบ

เอกสารนี้รวมรูปแบบการทำงานที่ผู้ดูแลโปรเจกต์ Hillstone Job API ชอบให้ AI ทำ ใช้ร่วมกับ `AGENTS.md` และ `docs/project_rules.md`

เมื่อขัดแย้งกัน ให้ยึดลำดับ: **ความปลอดภัย > กฎโปรเจกต์ > ความชอบส่วนบุคคล**

---

## 1. ภาษาและการสื่อสาร

* ตอบเป็น **ภาษาไทย** เป็นหลัก technical term ภาษาอังกฤษ (เช่น endpoint, subprocess, chunk) คงไว้ตามธรรมชาติ
* คำอธิบายให้กระชับ ไม่เยิ่นเย้อ ตัดบทพูดสุภาพที่ไม่จำเป็น
* ถ้ามีหลายทางเลือก ให้เสนอทางเลือกพร้อมเหตุผลสั้น ๆ แทนการถามปลายเปิด

---

## 2. ก่อนแก้ไข — อ่านก่อนเสมอ

ก่อนแก้ไขอะไรก็ตาม ให้:

1. อ่านไฟล์ที่เกี่ยวข้องจนเข้าใจ flow ปัจจุบัน
2. ตรวจว่าฟีเจอร์ที่จะเพิ่ม มีอยู่แล้วหรือไม่
3. ตรวจว่าเกี่ยวกับ VBA macros (`.bas`) หรือไม่ ถ้าเกี่ยว ต้องอัปเดตทั้งสองฝั่ง
4. ถ้างานเล็กและชัดเจน ทำเลย ไม่ต้องถาม

---

## 3. แนวทางการเขียนโค้ด

* **ทำน้อยที่สุด** เท่าที่แก้ปัญหาได้ — ห้าม over-engineer
* ใช้ library ที่มีอยู่ใน `requirements.txt` ก่อนเสมอ ถ้าจะเพิ่ม dependency ใหม่ต้องบอกเหตุผล
* เคารพ code style เดิม — ดูไฟล์ข้างเคียงก่อนเขียน
* ถ้าจะ refactor ใหญ่ หยุดถามก่อน
* เก็บ `print()` ไว้สำหรับ script ย่อย (จะถูก capture ลง log) และเก็บ exception handling ไว้ใน `api.py`

---

## 4. การแก้บั๊ก

เวลาช่วยแก้บั๊ก ให้ทำตามลำดับ:

1. ระบุอาการ
2. หาต้นเหตุ (อ่าน log ใน `job_logs/` หรือเช็ค schema DB)
3. อธิบายต้นเหตุสั้น ๆ
4. เสนอ fix
5. ทำ fix
6. ทดสอบด้วย `test_api_jobs.py --job all` ถ้าเป็นไปได้

ห้ามปิดบั๊กด้วยการ swallow exception หรือใส่ `try/except` กว้าง ๆ เพื่อให้ script ผ่าน

---

## 5. การจัดการ Database

* ก่อน `UPDATE` / `DELETE` ใน `logs_cyber` ให้ถามเสมอ — ตารางนี้เป็น append-only
* ก่อนเปลี่ยน schema ให้ตรวจว่า Excel VBA ที่ผู้ใช้ import ไปแล้วอ้างถึง column อะไรบ้าง
* ถ้าจะเปลี่ยนค่า default ของ `if_exists` จาก `append` ห้ามทำเด็ดขาด

---

## 6. การจัดการ Git

* อย่า commit เว้นแต่ผู้ใช้สั่ง
* อย่า push ขึ้น remote เว้นแต่ผู้ใช้สั่ง
* อย่า force push, reset hard, ลบ branch, หรือลบ uncommitted change ของผู้ใช้
* commit message ให้กระชับ บอกว่า "ทำอะไร" และ "ทำไม"

---

## 7. Security

* ไฟล์ `.env` ห้าม commit เด็ดขาด — ถ้าเห็นใน diff ให้เตือนทันที
* ห้าม echo / log / commit credentials ไม่ว่าจะ encoded หรือไม่
* API ไม่มี auth — ถ้าจะเพิ่ม feature ใหม่ที่ต้องเปิดเพิ่ม ให้เตือนเรื่อง firewall/reverse proxy
* ห้ามเปลี่ยน `0.0.0.0` ใน uvicorn โดยไม่ถาม

---

## 8. การทดสอบก่อนส่งมอบ

ก่อนบอกว่าเสร็จ ให้:

1. รัน `python -c "import ast; ast.parse(open('FILE').read())"` กับไฟล์ที่แก้ (syntax check)
2. ถ้าเป็นการเปลี่ยน API/CSV processing รัน `python test_api_jobs.py --job all` (ถ้า env พร้อม)
3. ถ้ารัน test ไม่ได้ ให้บอกชัดเจนว่าทำไม

---

## 9. การอัปเดตเอกสาร

* เปลี่ยน endpoint → อัปเดต `README_API.md`
* เปลี่ยน env vars / config → อัปเดต `README.md` + `.env.example` + `docs/project_rules.md`
* เปลี่ยน behavior ของ VBA → อัปเดต `*.bas` ที่เกี่ยวข้อง
* อย่าเขียน doc ใหม่เองถ้าไม่จำเป็น ให้แก้ของเดิม

---

## 10. การออกคำสั่งทำลายล้าง

ห้ามทำสิ่งเหล่านี้โดยไม่ถาม:

* `git reset --hard`, `git clean -fd`, `git push --force`
* ลบ branch
* ลบไฟล์ใน repo (ยกเว้นไฟล์ชั่วคราวที่ตัวเองสร้าง)
* `TRUNCATE` / `DELETE` ใน DB
* เปลี่ยน port, table name, หรือ env variable name
* restart API service ที่กำลังรัน production

ถ้าผู้ใช้สั่ง ให้ทำซ้ำให้ชัดเจนว่าจะทำอะไร รอบ ๆ ไหน แล้วค่อยทำ

---

## 11. การตอบคำถาม

* ถ้าผู้ใช้ถามแบบทั่วไป ให้ตอบสั้น ตรงประเด็น
* ถ้าเป็นงานที่กระทบหลายไฟล์ ให้สรุปแผนก่อนลงมือ
* ถ้าไม่แน่ใจ ให้ถามกลับด้วยตัวเลือก ไม่ใช่คำถามปลายเปิด
* ถ้าผู้ใช้สั่งขัดกับ project rules ให้เตือนก่อน 1 ครั้ง แล้วถามว่าจะดำเนินการต่อหรือไม่
